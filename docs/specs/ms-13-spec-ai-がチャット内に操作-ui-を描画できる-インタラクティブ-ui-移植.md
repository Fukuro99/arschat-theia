# ms-13 SPEC: AI がチャット内に操作 UI を描画できる (インタラクティブ UI 移植)

## 背景・なぜこのMSが必要か

レガシー ArsChat (移植元: C:\Users\takep\source\ArsChat) の看板機能に「インタラクティブ UI」がある。AI がチャットの返答の中にボタン・フォーム・スライダーや、サンドボックス (= 隔離された実行環境) 内の HTML 画面を描画し、ユーザーがそれを操作すると結果が AI に届いて会話が続く。チャットが「読むだけ」から「触れる」体験になる機能で、レガシー版ユーザーが新版に乗り換えるための必須条件のひとつ。

Theia 版 (このリポジトリ) は ms-15 (ファイルブラウザ・検索・アウトライン) までにチャットの基本体験・ツール実行カード・画像添付などが揃ったが、AI の出力は依然テキストと画像のみ。この MS をやらないと、レガシーで日常的に使われていた「AI にアンケートフォームを出させる」「ミニゲームやシミュレーション画面を作らせる」といった使い方が新版で成立せず、移行の壁が残り続ける。

## 解決すべき問題

| # | 問題 |
|---|---|
| 1 | AI がチャット内に操作可能な UI (ボタン・フォーム・スライダー等) を出す手段がない |
| 2 | ユーザー操作を AI に返す経路が、ツール実行の承認カード (許可/拒否) 専用で、フォーム送信やライブ操作には使えない |
| 3 | AI が生成した HTML を安全に隔離実行して表示する基盤 (表示専用・操作通知付きの両方) がない |
| 4 | スキル (= スラッシュコマンドで発動するオプトイン指示、ms-5 で実装済み) はプロンプト注入専用で、「スキルに応じてツール群を出し分ける」仕組みがない |

## 設計方針 (判断軌跡)

### 1. 宣言方式は tool call (= AI が機能を呼び出す仕組み) に再設計する

- レガシーは「コードブロック + JSON を返答テキストに埋め込む」方式だったが、これは採らない。
- 理由: Theia には ToolProvider / ToolInvocationRegistry / ToolCallChatResponseContent という確立されたツール呼び出し経路があり、承認カード実装 (ms-6 の M5、arschat-chat-widget の wireToolCall) で「ユーザー操作 → promise 解決 → 結果を LLM に注入」の型が既に実証済み。ここに乗るのが最も自然で堅牢。
- 理由 (2): レガシーの正規表現パーサはストリーミング途中の壊れた JSON や記法ゆれに弱かった。tool call ならスキーマがツール定義として自己記述的になり、モデル側の記法ミスも減る。
- 却下した代替案: レガシー忠実移植 (コードブロック方式)。プロンプト資産をそのまま使える利点はあるが、パーサの脆弱性と描画パイプラインの複雑化を新版に持ち込むため見送り。レガシーとのプロンプト互換は捨てる。

### 2. UI 部品 (プリミティブ) の描画実装はレガシーから流用移植する

- box / grid / text / icon / badge / progress-bar / image / button / input / select / checkbox / slider / chips / clickable 等 16 種の React 実装・デザイントークン・未知部品のフォールバック表示は、宣言方式と独立しているのでそのまま流用できる。
- 理由: 実戦投入済みの実装を書き直すのは無駄。移植コストを描画層ではなく経路の再設計 (方針 1) に集中させる。
- 注意: input 部品は CORE doc「IME を扱う入力欄は uncontrolled で作る」(日本語入力が消える不具合の再発防止原則) に従って移植時に作り替える。

### 3. サンドボックス HTML は iframe + Blob URL + sandbox="allow-scripts" を踏襲する

- allow-same-origin は付与せず、親子間の通信は postMessage (= 隔離された画面と親アプリの間の限定メッセージ通路) のみ。外部ネットワークへのアクセスは不可。
- 理由: レガシーで実証済みの隔離境界であり、AI 生成コードを実行する以上ここは弱められない。画像 URL の許可リスト (data:/blob:/相対パスのみ) も同様に踏襲。

### 4. ユーザー操作は「ツール結果」として AI に返すことを基本形にする

- フォーム (default モード): UI 描画ツールの呼び出しはユーザーが送信するまで完了せず、送信データがツール結果として AI に返る。
- ライブモード (操作のたびに AI が画面を更新し続ける形): 操作をツール結果で返し、AI は更新ツールで差分 (patch) を送り返す。差分の取り込みルール (オブジェクトは再帰マージ・配列は上書き・status=finished で終了) はレガシーの設計を踏襲。
- 理由: 承認カードと同じ「promise 解決」の型に揃えることで、チャット履歴を汚す隠しメッセージ方式 (レガシーの方式) が不要になる。

### 5. 既存スキル機構 (ms-5 実装済み) に組み込みスキルとして統合し、ツール公開ゲートを追加する

- Theia 版には既にスキル機構がある (markdown + frontmatter を `${configDir}/arschat/skills/*.md` から読み、スラッシュコマンドで発動、本文をプロンプトに展開する SkillService)。これを新設するのではなく、インタラクティブ UI を組み込みスキルとして seed し、「スキル発動中は UI ツール群をエージェントに公開する」ゲートを SkillService / エージェント連携に追加する。
- 理由: レガシーの skill-manager と同じ「オプトインで有効化」の体験を、既存資産の最小拡張で実現できる。常時全ツールを公開するとツール定義とシステムプロンプトが肥大し、UI が不要な場面でもモデルが気を取られる。
- 訂正の記録: SPEC 初稿では「スキル機構が存在しないため骨格から新設」と誤認していた。ms-5 の SkillService 実装を確認して本方針に差し替えた。

## スコープ

### やる
- プリミティブ UI (default + ライブモード) のツール化と描画
- 表示専用サンドボックス HTML (レガシーの iframe 方式相当)
- 操作通知付きサンドボックス HTML (レガシーの interactive-html 相当)
- インタラクティブ UI の組み込みスキル追加と、スキル連動のツール公開ゲート (既存 SkillService の拡張)
- 送信済み・終了済み UI の再操作防止、不正入力時のフォールバック表示
- 自動検証 (ARSCHAT_M13_AUTOTEST) と jest ユニットテスト、BUILD_NOTES への実装記録

### やらない (別MS or 後回し)
- レガシーのコードブロック記法 (```interactive-ui 等) の互換パース — プロンプト互換は捨てる判断 (方針 1)
- スキル機構そのものの再設計 — ms-5 の実装を活かし、ツール公開ゲートの追加に留める
- サンドボックスからの外部ネットワークアクセス許可 — セキュリティ境界として恒久的にやらない
- レガシーの WidgetOverlay (デスクトップ常駐ミニチャット) — 本機能とは無関係

## 受入条件 (AI 推測 — 修正自由)

1. スキルを発動すると、AI がツール呼び出しでボタン・入力欄・選択肢・チェックボックス・スライダーを含むフォームをチャット内に描画できる
2. フォームの送信ボタンを押すと入力データが AI に届き、AI がその内容を踏まえた応答を返す
3. ライブモードで「ユーザー操作 → AI が差分を返す → 画面が更新される」の往復が成立し、AI が終了を宣言すると UI が操作不能になる
4. 表示専用 HTML が隔離 iframe 内に描画され、外部ネットワークへのアクセスができないことが確認できる
5. 操作通知付き HTML で、iframe 内のボタン操作が AI に届き、AI の差分が iframe に反映される
6. 送信済みフォームは再送信できず、「送信済み」表示に切り替わる
7. AI が不正な JSON や未知の部品名を出しても、アプリはクラッシュせずフォールバック表示になる
8. スキルの発動有無で、AI に公開されるツール群が実際に増減する
9. ARSCHAT_M13_AUTOTEST=1 での自動検証が PASS する (描画・往復・無効化の各シナリオ)
10. スキーマ検証・差分マージ・部品レジストリの jest テストが既存スイートに追加され、全件 green

## 実装順序のヒント (AI 推測 — 修正自由)

1. スキル連動のツール公開ゲート (SkillService とエージェントの連携拡張) — ツールの出し分けの土台
2. プリミティブ 16 種 + 描画レンダラの移植 (まず静的描画のみ)
3. UI 描画ツール + フォーム送信往復 (default モード) — 中核の縦切り
4. ライブモード (状態管理・更新ツール・差分マージ)
5. サンドボックス HTML (表示専用 → 操作通知付きの順)
6. 自動検証 (M13 AUTOTEST + jest) と BUILD_NOTES 追記

工程の分担方針 (ユーザー指定): 調査は Sonnet、実装とレビューは Codex (別セッション)、複雑な設計判断は Opus に委譲する。
