# ms-14 SPEC: ArsChat 独自拡張を GitHub から権限確認付きで設置できる

## 背景・なぜこのMSが必要か

旧 ArsChat (Electron 版、移植元リポジトリ) の差別化機能のひとつが「ユーザーが自作した拡張を GitHub から入れて、チャットアプリを自分好みに育てられる」体験だった。Theia 版 (本リポジトリ) には ms-12 (VS Code 系拡張を Open VSX から検索・設置できるようにしたマイルストーン) があるが、あれは開発者向けエコシステムの話であり、「軽量な ArsChat 独自形式の拡張」の受け皿はまだ無い。

ただし移植元の実装を調査 (2026-07-20、コード実測) した結果、旧拡張システムには看板と実態の深刻な乖離があることが分かった:

- 「権限確認付き」を謳うドキュメントに反して、権限確認ダイアログは未実装 (URL 入力 → 即設置 → 即実行)
- 権限宣言は自己申告制で技術的強制力ゼロ。拡張コードは Electron の中枢プロセスに直接読み込まれるため、権限ゼロ宣言でもファイル操作やシェル実行が素通しでできる (同梱サンプル拡張に実例あり)
- 拡張の画面もドキュメントの「iframe (= 隔離された表示枠) で実行」に反して、実装はアプリ本体と同じ空間への直接読み込みで隔離ゼロ

つまりこの MS は「旧コードの移植」ではなく、「旧版がやりたかったが実現できていなかった設計を、Theia 版で正しく作り直す」マイルストーンである。放置すると、旧版ユーザーの拡張体験が引き継がれないだけでなく、将来他人の拡張を入れられるようになった時の安全基盤が無いままになる。

## 解決すべき問題

| # | 問題 |
|---|---|
| 1 | Theia 版に ArsChat 独自形式の拡張を設置・実行する仕組みがそもそも無い |
| 2 | 旧実装は設置時の権限確認 UI が無く、「入れる = 全権を渡す」になっていた |
| 3 | 旧実装の権限宣言は強制力が無く、悪意ある拡張は宣言を無視して何でもできた |
| 4 | 旧実装の設置フローは git clone + npm build (= 設置しただけで相手のビルドスクリプトが実行される) で、設置自体が任意コード実行だった |
| 5 | 旧実装はドキュメントと実装が乖離しており (iframe と書いて直接読み込み等)、拡張作者が正しいコードを書けなかった |

## 設計方針 (判断軌跡)

### 1. 拡張 UI はサンドボックス iframe で実行し、権限を構造的に強制する

- やり方: 拡張の画面は ms-13 (AI がチャット内にフォームやライブ更新 UI を出せるようにしたマイルストーン) で作ったサンドボックス HTML 基盤を土台に、隔離された iframe 内で実行する。アプリ側 API は postMessage (= 枠を越えてメッセージだけをやり取りする通信手段) のブリッジ経由でのみ提供し、承認された権限に対応する API だけをブリッジに載せる。
- 理由: 旧実装の「宣言だけの権限」は見せかけの安全性であり、確認ダイアログを足しても意味が無い。境界を構造にすれば「権限外のことはそもそも呼べない」が保証でき、確認ダイアログの承認が実質を持つ。
- 却下した代替案: 旧実装同等の直接読み込み + 確認ダイアログのみ (穴が残る)。Node.js 側の拡張実行 (旧 main.js 相当) も当面非対応とし、境界を「iframe 1 枚」に保って実装と監査を単純にする。

### 2. 拡張 API は Theia 版として新設計する (旧 API との互換は取らない)

- やり方: permissions 宣言を持つ manifest (= 拡張の自己紹介ファイル) という考え方は旧版から引き継ぎつつ、API の形は postMessage ブリッジ前提で新設計する。権限の粒度は read / write を分離し、旧実装の「fs:read だけで書き込み・削除まで解放される」ような一括解放はしない。
- 理由: 旧 API は Electron 中枢プロセス前提でサンドボックス方式と根本的に相容れない。しかもドキュメントと実装が乖離しており、互換を取る対象の「正」が存在しない。ここでリセットし、ドキュメント = 実装を一致させて再出発する。
- 旧サンプル拡張 (test-extensions の 5 個) は手で移植する前提。

### 3. 設置は「ビルド済みファイル取得」と「ローカルパス開発モード」の両対応

- やり方: 通常の設置は GitHub リポジトリからビルド済み成果物 (manifest + バンドル済み JS/HTML) だけを取得し、設置時にコードを一切実行しない。拡張開発者向けには、ローカルパス指定で手元の拡張をそのまま読み込む開発モードを用意する。
- 理由: 旧方式の clone + npm build は「設置ボタン = 相手のスクリプトを実行するボタン」であり、権限確認の意味を壊す。一方でローカル開発の回しやすさは旧版の良さなので、開発モードとして残す。
- 署名検証やチェックサムは今回はやらない (将来の配布基盤の話として切り離す)。

### 4. 権限確認ダイアログを設置フローの必須ステップにし、承認を永続化する

- やり方: 設置前に「この拡張が要求する権限」を日本語の説明付きで一覧表示し、承認しない限り設置しない。承認結果は保存し、更新で要求権限が増えた場合は増分を再確認する。
- 理由: 旧実装は更新 (git pull) で権限が増えても無確認で反映されるという穴があった。「一度入れたら何でも増やせる」を塞がないと初回確認が形骸化する。

## スコープ

### やる

- 拡張 manifest 形式と権限種別の定義 (read / write 分離の粒度)
- GitHub リポジトリからのビルド済み成果物の取得・設置
- ローカルパス指定の開発モード設置
- 設置時 (および権限が増える更新時) の権限確認ダイアログと承認の永続化
- サンドボックス iframe での拡張 UI 実行 + 権限ゲート付き postMessage API ブリッジ (チャット送信・読み取り、拡張専用の保存領域など最小セット)
- 拡張の一覧・有効/無効・削除・更新ができる管理 UI
- 新 API 準拠のサンプル拡張と、実機自動検証 (ARSCHAT_M14_AUTOTEST)

### やらない (別MS or 後回し)

- Node.js 側で動く拡張 (旧 main.js 相当のバックエンド実行) — 境界を増やすため当面非対応
- 旧 ArsChat 拡張の互換層・自動移行
- 拡張のマーケットプレイス・検索・カタログ (URL 手入力で足りる。Open VSX 検索は ms-12 が担当)
- 署名検証・チェックサム・バージョン固定などの配布基盤強化
- hooks (= アプリ内イベントの観察 API) の提供 — API 面を最小に保つため後回し

## 受入条件 (AI 推測 — 修正自由)

1. GitHub リポジトリの URL を指定して ArsChat 独自拡張を設置できる (設置時に拡張側のコードやビルドスクリプトは実行されない)
2. 設置前に要求権限の一覧が日本語説明付きで表示され、承認しない限り設置されない
3. 承認した権限は保存され、アプリ再起動後も保持される
4. 更新で要求権限が増えた場合、増えた分の再確認ダイアログが出る
5. 拡張 UI はサンドボックス iframe 内で動作し、承認されていない権限の API 呼び出しはエラーになる (アプリ本体の DOM や内部状態には触れない)
6. 未承認権限の API が構造的に呼べないことが自動テストで確認できる
7. ローカルパス指定で開発中の拡張を設置・動作確認できる
8. 管理 UI から拡張の一覧表示・有効/無効切り替え・削除・更新ができる
9. 新 API 準拠のサンプル拡張が少なくとも 1 つ実機で動く
10. ARSCHAT_M14_AUTOTEST で上記の主要経路が自動検証され、結果が BUILD_NOTES に記録される

## 実装順序のヒント (AI 推測 — 修正自由)

1. manifest 形式と権限種別の型定義 + 読み込み検証 (これが決まらないと他が書けない)
2. サンドボックス iframe ホスト + 権限ゲート付き postMessage API ブリッジ (ms-13 基盤の再利用範囲をここで見極める)
3. ローカルパス開発モード設置 → サンプル拡張を新 API で書いて動作確認 (GitHub 取得より先に実行基盤を固める)
4. 権限確認ダイアログ + 承認の永続化 (更新時の増分再確認含む)
5. GitHub からのビルド済み成果物取得・設置
6. 拡張管理 UI (一覧・有効/無効・削除・更新)
7. ARSCHAT_M14_AUTOTEST + BUILD_NOTES 記録
